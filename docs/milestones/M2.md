# M2: shell and state

**Exit criterion:** the playground's terminal is xterm.js running a real shell (BusyBox) on a
kernel PTY. In it, `npm create vite` → `npm install` → `npm run dev` works with Ctrl+C and job control.
Reloading the page keeps the project, and an embedder can snapshot, restore and fork it in
milliseconds through the SDK.

M2 is split into three sub-milestones. Each has its own exit criterion and leaves the system
working.

| # | Sub-milestone | Exit criterion |
|---|---|---|
| **M2a** | **Terminal** ✅ | The playground's terminal is xterm.js on a kernel PTY. `sh` is interactive, with history and line editing, and Ctrl+C returns to its prompt. Programs see a real TTY (colors, size, raw mode, `SIGWINCH`). Ctrl+C reaches `process.on('SIGINT')`, and `node` with no arguments starts Node's REPL. M1a's carry-over: a curated slice of Node's `test/parallel` runs |
| **M2b** | **State** ✅ | A content-addressed, copy-on-write VFS (ADR-0007), persisted as workspaces in OPFS (ADR-0019). `runtime.snapshot()`, `restore()` and `fork()` in the SDK. Reloading the page keeps the project. (The lazy-HTTP mount moves to M3, where Python's standard library needs it.) |
| **M2c** | **Real shell** ✅ | A C toolchain in the build (wasixcc), and a WASIX personality: `vfork` (the program acts as its child until `exec`), `exec`, `waitpid`, signal handlers, terminal calls. BusyBox built for systems without an MMU, which needs no `fork()`: `hush` as the shell, with line editing and job control (`Ctrl+Z`, `bg`, `fg`), plus coreutils, grep, sed, awk, vi and less. It replaces the hand-written WAT programs, and becomes `/bin/sh`. (bash needs a real `fork()`, through Asyncify; it comes later if needed.) |

M2c changed after research: no maintained WASIX port of bash or BusyBox exists, and WASIX's
exception-handling toolchain implements `vfork` without `fork`, which BusyBox's no-MMU
configuration needs and nothing more ([M2c approach](#m2c-approach)).

The order puts the visible gap first. The terminal is also something M2c needs. State comes next
because the agent API (M4) and replay (M5) build on snapshots. The real shell carries the most risk
(Asyncify-based `fork`, the repo's first C toolchain), and the TypeScript `sh` covers the need until
then.

## M2a approach

**Signals are delivered, not just enforced.** Today `kill` terminates the target immediately.
M2a gives each process a disposition per signal: default, ignore, or handle.
- **Default actions** follow Linux:
  - terminate: `INT`, `TERM`, `HUP`, `QUIT`, `PIPE`, `ALRM`, `USR1`, `USR2`
  - ignore: `CHLD`, `WINCH`, `URG`, `CONT`
  - stop: `TSTP`, `TTIN`, `TTOU`, `STOP`. These are ignored until job control arrives in M2c.
- **Handled signals** travel to the process over its message port. Node's `signal_wrap` turns them
  into `process.on('SIGINT')` callbacks. `SIGKILL` always terminates.

**A PTY in the kernel.** `openpty` creates a master/slave pair. The slave is a terminal: `isatty`
is true, and it has termios settings. A subset of Linux's line discipline sits between the two ends:
- **Canonical mode:** line buffering, echo, erase (`DEL`, `^H`), kill line (`^U`), erase word
  (`^W`), and `^D` for end of file.
- **Raw mode:** `ICANON` off, with `VMIN`/`VTIME`.
- **Output processing:** `ONLCR`, which turns `\n` into `\r\n`.
- **`ISIG`:** `^C` sends `SIGINT` and `^\` sends `SIGQUIT` to the foreground process group.
- **Window size:** `TIOCSWINSZ` sends `SIGWINCH` to the foreground group.
- **Hang-up:** when the master closes, the session gets `SIGHUP`.

An `ioctl` syscall carries the termios and terminal requests in Linux's numbering (ADR-0003):
`TCGETS`, `TCSETS` (and `TCSETSW`, `TCSETSF`), `TIOCGWINSZ`, `TIOCSWINSZ`, `TIOCGPGRP`,
`TIOCSPGRP` and `TIOCSCTTY`. Processes gain session ids. `setsid` and a controlling terminal
decide where `^C` goes.

**Node sees a TTY.**
- `guessHandleType` reports `TTY` for a terminal.
- `tty_wrap` reads the real window size and switches raw mode through `ioctl`. It restores the
  terminal's mode when the process exits, as libuv does.
- `process.stdout.isTTY`, colors and `columns` follow. The terminal's environment sets `TERM` and
  `COLORTERM`.
- `node` with no arguments starts Node's REPL, which needs whatever part of `vm` contexts `repl`
  uses.

**`sh` becomes interactive.** With a terminal on stdin (or `-i`), `sh` reads lines with Node's own
`readline`, which brings history, line editing and the real raw-mode path. Each foreground job runs
in its own process group, and `sh` hands it the terminal with `TIOCSPGRP`. `sh` ignores `SIGINT`
itself, so `^C` stops the job and returns to the prompt. A login shell (`-l`) reads `/etc/profile`.

**Embedding.** `runtime.openTerminal({ cols, rows, command })` starts a program on a new PTY and
returns an object with `write`, `resize`, `kill` and `exited`. Its output streams like other jobs
(ADR-0017). The playground's terminal becomes xterm.js on it. Example buttons type their command
into the terminal.

**Carry-over from M1a:** a runner for Node's `test/common` and a curated slice of `test/parallel`,
with the pass list checked in, so regressions show up.

## M2a status: done

The playground's terminal is xterm.js on a kernel pseudo-terminal, running `sh -l`: a colored
prompt, history, line editing and tab completion. In it, `npm create vite`, `npm install` and
`npm run dev` work. Vite sees a TTY and offers its keyboard shortcuts (`h` + Enter), HMR updates the
preview, and Ctrl+C stops the server and returns to the prompt. `node` starts Node's REPL, with
colors and tab completion.

What works:
- **Signals** (ADR-0018): dispositions per process (`sigaction`), Linux's default actions, and
  handled signals delivered over the process's port. Node's `process.on('SIGINT')`, `'SIGTERM'`,
  `'SIGWINCH'` and `process.kill(pid, …)` behave as in Node, with exit status 128 + signal
  otherwise.
- **Pseudo-terminals:** `openpty` and a subset of Linux's line discipline:
  - canonical editing (erase, kill, word erase, reprint, literal next), echo with `ECHOCTL`, and
    `^D`
  - raw mode with `VMIN`/`VTIME`, and `ONLCR`
  - `^C`, `^\` and `^Z` as signals to the foreground group
  - window size with `SIGWINCH`, and hang-up when the terminal closes
- **Sessions and groups:** `setsid`, `setpgid`, `getsid`, a controlling terminal, its foreground
  group (`TIOCSPGRP`), and `SIGHUP` for the foreground job when the session leader exits. A
  background read waits until its group is in the foreground.
- **Node on a TTY:**
  - `isTTY`, `columns`/`rows`, color depth (`TERM`, `COLORTERM`), and resize events
  - `setRawMode`, with the terminal's mode restored at exit
  - blocking TTY writes, as libuv makes them
  - the REPL: `node` with no arguments, or `-i`
- **`vm` contexts:** `createContext`, `runInContext` and `runInNewContext`, approximated in one
  realm. Names resolve to the sandbox and the context's builtins, never to the process's globals.
  Top-level `var` and function declarations land on the sandbox. `repl` now loads: 69 of 72 builtin
  modules.
- **Interactive `sh`:**
  - Node's `readline` for input, with `PS1`/`PS2` (bash's escapes) and completion of commands and
    paths
  - job control: each pipeline in its own process group, in the foreground
  - `^C` at the prompt or for a job, `^D` to exit, a login profile (`/etc/profile`), and `clear`
- **SDK:** `runtime.openTerminal({ cols, rows, command, onData })` returns `write`, `resize`,
  `close` and `exited`. The playground's example buttons type into the terminal.
- **Node's own tests:** `pnpm test:node` runs Node v24.21.0's `test/parallel` files listed in
  `packages/kernel/test/node-parallel.txt`: 2,746 of the 4,543 files (2,140 pass, 606 skip on
  platform grounds), in about 2.5 minutes. A failure there is a regression. `--all` runs every
  file (about 6.5 minutes), and `--update` refreshes the list.

Not done, and why:
- **Stop and continue** (`^Z`, `bg`, `fg`): a Worker can't be paused. That needs processes that
  check in with the kernel, and comes with bash in M2c.
- **Interrupting busy code:** a handled signal runs once the program yields. The REPL can't break
  out of an infinite loop with Ctrl+C (Node's SIGINT watchdog).
- **`SIGPIPE`** isn't raised; writes to a closed pipe fail with `EPIPE` only.
- **`vm` contexts** share builtins with the main context, read undeclared names as `undefined`,
  and don't keep top-level `let`/`const` between runs. A Worker can't create a realm.

### What M2a taught us

- **Real programs exercise the terminal's corners.** Node's `readline.pause()` keeps raw mode, so
  `^C` reached a running job as a plain byte until the shell switched modes around each job, as
  bash's readline does. A paused shell's read was still pending in the kernel and stole the job's
  first line until terminal reads waited for the foreground.
- **A terminal changes what programs do.** create-vite asked which linter to use, Vite offered
  shortcuts, and `node -p` printed in color. All correct, and all invisible while stdio was pipes.
  The playground's example now passes `--no-interactive`.
- **Node's own tests are the honest measure.** The first full run of all 4,543 files gave a
  baseline to protect, and the failures are a to-do list by module. Most come from what isn't
  planned yet: `http2` (264), `tls` (188), `https` (63), `dgram` (63), `cluster` (55),
  `permission` (37), plus `crypto` (107) and `webcrypto` (46) without OpenSSL. Among implemented
  modules, `fs` (100), `vm` (63), `child_process` (61), `http` (52) and `worker_threads` (52) have
  the most.
- **Exit before output is a real race.** One listed test failed now and then: a child's `'exit'`
  arrived before its last stdout. The kernel reports an exit and a pipe's data on separate
  messages, while libuv practically always delivers the data first. The child-process handle now
  waits for its stdio pipes to drain (50 ms at most) before `onexit`, and programs that collect
  output until `'exit'` get all of it. One other test was timing-sensitive under load and was
  left off the list.

## M2b status: done

Reloading the playground keeps the project. `/home`, `node_modules` included, comes back from the
workspace's saved state in the runtime origin's storage, and `npm run dev` starts again without
reinstalling. The page is ready about 0.15 s after the reload. A second tab on the same workspace
loads it read-only and says so. "Fork in a new tab" opens a copy that saves on its own.

What works:
- **Content-addressed storage** (ADR-0007): file contents and link targets are SHA-256 blobs,
  and directories are git-like trees. Identical contents are stored once.
- **Snapshots** hash only what changed: nodes keep their hash until they change, and a directory
  whose listing is the same keeps its tree hash. For 5,000 files (24.6 MB): 0.2 s the first time,
  about 10 ms after a change.
- **Restore is copy-on-write.** It builds nodes over the stored blobs without copying them; a
  file copies its data on the first write. Restoring 5,000 files takes about 50 ms. Watchers get
  an `fs.change` event for each difference, so a dev server reloads what a restore changed.
- **Workspaces** (ADR-0019): saves a second after changes stop (at least every 10 s), as packs of
  new objects plus a record of the head. A fork is a workspace that starts from a snapshot. Web
  Locks allow one writer per workspace, and compaction only when no other runtime is open.
- **SDK:** `connect({ workspace, from })`, `runtime.snapshot()`, `runtime.restore(id)`,
  `runtime.fork()`, and `RuntimeInfo.workspace`. A fork boots in about 0.3 s.
- **Events:** `fs.snapshot`, `fs.restore` and `workspace.save` (ADR-0010). The playground shows
  when it last saved.
- **Playground:** a workspace from `?workspace=`, plus "Snapshot /home", "Restore snapshot" and
  "Fork in a new tab".

Not done, and why:
- **Lazy-HTTP and other mounts:** a read-only tree fetched on demand pays off for large runtime
  images. That's Python's standard library, in M3, so the mount comes then. Overlays exist as the
  copy-on-write trees that restore builds.
- **Instant installs from the store:** npm could graft a package's tree by integrity instead of
  downloading and unpacking it again. The blobs are already shared; skipping the download needs
  npm to ask the kernel first.
- **Dropping snapshots:** kept snapshots stay until a future API removes them.
- **Export and import:** packs could leave the browser (sync, sharing, templates), but there's no
  API for that yet.

### What M2b taught us

- **Defer, cache, compare.** Hashing on every write would have taxed every syscall. Hashing at
  snapshot time, with each node's hash cached until it changes, and comparing a directory's listing
  before rehashing it, makes the second snapshot of a large tree cost about 10 ms.
- **Copy-on-write needs one flag.** Restored files point at blobs and copy on the first write.
  The bug to avoid was copying only the bytes up to the write: a 2-byte write into a 100-byte
  file would have lost the rest.
- **A restore is a change like any other.** Diffing the old and new tree hashes yields exactly the
  `fs.change` events a watcher needs, and only subtrees whose hashes differ are compared.
- **The browser decides storage boundaries.** OPFS in a third-party frame is partitioned by the
  embedding site, so workspaces are per embedder. Web Locks made "one writer per workspace" and
  "compact only when alone" a few lines each.

## M2c approach

**Toolchain.** `packages/wasix-bin` downloads wasixcc and its LLVM, WASIX sysroot and binaryen
at pinned versions into a cache, and builds C programs from source at pinned versions. Builds use
the exception-handling sysroot: `setjmp`/`longjmp` are Wasm exceptions, and there's no Asyncify.

**vfork without fork.** In that sysroot, `vfork()` is `setjmp` plus `proc_fork_env`. The kernel
creates the child process (a copy of the fd table, working directory, environment and signal
dispositions), and the calling program acts as the child until it calls `exec` or `_exit`. Its
syscalls go to the child: `dup2`, `setpgid` and so on. `exec` then starts the new program in the
child, and `_exit` ends it. Either call returns in the parent, which `longjmp`s back to `vfork`.
No memory is copied and nothing is unwound.

**The WASIX personality** is preview1 plus the `wasix_32v1` calls that BusyBox and its libc use:
- process calls: `proc_fork_env`, `proc_exec*`, `proc_exit2`, `proc_spawn*`, `proc_join`
  (waitpid), `proc_signal`, `proc_id`/`proc_parent`
- `callback_signal` and signal delivery between syscalls
- file descriptor calls: `fd_dup`/`fd_dup2`/`fd_pipe`/`fd_fdflags`, and `getcwd`/`chdir`
- `tty_get`/`tty_set`, futexes for a single thread, and an imported shared memory

(Building it showed that wasix-libc answers much of the rest from the program's own memory:
process groups, the foreground group, termios, signal dispositions. libwebcore, a small library
every program links, sends those to the kernel. See the status below and ADR-0020.)

**Job control.** A stopped process is one whose syscalls the kernel holds until `SIGCONT`.
`waitpid` reports stopped and continued children. The terminal's `^Z` and hush's `bg`/`fg` work
on that.

**BusyBox** is built from pinned source, configured for no MMU, with hush, line editing and
coreutils. Its applets are installed as symbolic links. It becomes `/bin/sh` (in place of the
TypeScript `sh`, which starts a whole Node process), and the WAT programs go away.

## M2c status: done

The playground's terminal runs BusyBox's hush as a login shell, on the same kernel PTY as before:
a colored prompt, line editing, history, tab completion, and job control. `^Z` stops the job in
the foreground, `jobs` lists it, and `fg` and `bg` continue it, whether it is a C program or Node.
`ls -l` shows modes and owners, `vi` and `less` run full screen, and `npm create vite`, `npm
install` and `npm run dev` work as before, now through hush.

What works:
- **A C toolchain in the build:** `@webcore/wasix-bin` downloads wasixcc 0.4.7, WASIX's LLVM 21,
  the exception-handling sysroot and binaryen at pinned versions, and builds BusyBox 1.38.0 from
  checksummed source with two patches. `pnpm build` skips it while its inputs are unchanged.
- **BusyBox** (577 KB of Wasm), built for systems without an MMU: hush as `/bin/sh` with
  arithmetic, functions, `case`, here-documents, `trap`, `wait`, `read -t` and job control, and
  over a hundred applets: coreutils, `grep`, `sed`, `awk`, `find`, `xargs`, `diff`, `patch`, `tar`,
  `gzip`, `unzip`, `vi`, `less`, `bc`, `timeout` and more. Each is a symbolic link to
  `/bin/busybox`.
- **The WASIX personality** (ADR-0020):
  - fds are the kernel's own; `/` is a virtual preopen just past them
  - `vfork`, nested two deep, and `execve`, in a new Worker or in place, closing `FD_CLOEXEC` fds
  - `wait4` with `WNOHANG`, `WUNTRACED` and `WCONTINUED`, and `SIGCHLD`
  - `posix_spawn`, pipes, `dup`/`dup2`, `poll` on pipes, terminals and sockets
  - a shared imported memory, and futexes
- **Signals between syscalls:** a doorbell in the syscall page, `EINTR` for blocked calls, and
  `SA_RESTART`. Handlers, ignored signals and default actions work alike for C and Node programs.
- **Job control:** `SIGTSTP`, `SIGSTOP`, `SIGTTIN` and `SIGTTOU` stop a process by holding its
  syscalls; `SIGCONT` continues it.
- **libwebcore**, linked into every program: the kernel's process groups, sessions, termios,
  foreground group, signal dispositions, file modes, umask and times, plus fixes for wasix-libc's
  nested vfork, `execv` and `utimensat`.
- **Kernel additions:** `vfork`, `vforkExit`, `execve`, `wait4`, `dup`, `dup2`, `fdflags`,
  `chmod`, `utimes`, `umask`, `poll`, `pause`, `getpgid`, `takeSignals`, and `O_CLOEXEC`. Node's
  `fs.chmod`, `fs.utimes` and `process.umask` use them too. An exiting shell's stopped jobs get
  `SIGHUP` and `SIGCONT` (orphaned process groups), and `kill` reaches an exited child until its
  parent waits.
- **Hosts:** `runLine` (the SDK's `createShell`) runs each line with `/bin/sh` and keeps the
  working directory and exported variables. `installRootfs` installs BusyBox and its links, plus
  `/etc/passwd` and `/etc/group` for the one user.
- **Retired:** the TypeScript `sh`, the host-side mini shell and the hand-written WAT programs.
  Two of the WAT programs remain as test fixtures for plain preview1 modules and `node:wasi`.
- **Tests:** `wasix.test.ts` covers vfork, exec, signals, terminals, modes, traps, stop and
  continue, `timeout` and `read -t`; the terminal tests cover `^Z`/`fg`/`bg`, line editing, and
  `vi` and `less`. Every listed file of Node's `test/parallel` still passes, and a full run passes
  at least 18 more than before (2,158), now that modes, times and umask are real.

Starting a program costs a Worker plus an instantiation, about 40 ms headless with warm Workers.
hush runs its own built-in applets in-process.

Not done, and why:
- **bash**, and other programs that need a real `fork()`: that needs Asyncify. BusyBox needs only
  vfork.
- **Interrupting a busy loop** for a handled signal: the handler runs at the next syscall. Default
  actions, stops and `SIGKILL` take effect at once.
- **Threads in WASIX programs** (`thread_spawn`): BusyBox has none.
- **Networking applets** (`wget`, `nc`): WASIX's socket calls aren't mapped to the kernel's
  sockets yet.
- **`SIGTTIN`/`SIGTTOU`:** a background reader of the terminal still waits rather than stops, and
  `tcsetpgrp` from the background doesn't stop the caller.

### What M2c taught us

- **vfork is enough for a shell.** BusyBox has run on systems without an MMU for decades, so its
  shell and applets already do everything with vfork and exec. That avoided Asyncify entirely.
- **A libc can hide a lot of Linux in memory.** wasix-libc keeps signal dispositions, the process
  group, the foreground group and most of termios in program variables, so the kernel couldn't
  see them. Wrapping about twenty functions at link time put them back in the kernel, without
  building a libc.
- **Real programs find real bugs.** BusyBox exposed five: wasix-libc's two `environ`s, `execv`
  passing no environment, `UTIME_NOW` rejected, nested vfork returning to a dead frame, and a `-p`
  option BusyBox's no-MMU `timeout` never parsed. A real shell then let Node's own `test/parallel`
  catch two of ours: Node didn't reopen closed stdio on `/dev/null`, and `kill` failed for a child
  that had exited before Node saw its exit (Linux keeps it as a zombie until then).
- **Bytes aren't always UTF-8.** BusyBox marks a re-executed `argv[0]` by setting a high bit, so
  arguments cross the kernel as strings that keep invalid bytes (as Python's surrogateescape).
