# M1: the flagship

**Exit criterion:** `npm create vite@latest app -- --template react` → `cd app` → `npm install` →
`npm run dev`, with the React app live in a preview pane and HMR working. Everything runs in the
browser tab.

That single command line touches almost every subsystem, so M1 is split into six sub-milestones.
Each has its own exit criterion and leaves the system working.

**Status:** the exit criterion is met in the browser as of M1e, and since M1f the kernel runs in an
isolated runtime frame on its own origin. Still open: M1a's slice of Node's `test/parallel`.

| # | Sub-milestone | Exit criterion |
|---|---|---|
| **M1a** | **Real Node boots** (mostly done, see below) | `/usr/bin/node` runs Node v24.21.0's own `lib/` over kernel bindings. The M0 end-to-end suite passes unchanged, the M0 shim is deleted, and a curated slice of Node's `test/parallel` passes |
| **M1b** | **ES modules** ✅ | `module_wrap` implemented (ADR-0013); `import.meta`, dynamic `import()`, CJS↔ESM interop including `require(esm)`. `create-vite`'s CLI runs |
| **M1c** | **Networking and preview** ✅ | Virtual TCP in the kernel (`tcp_wrap`, `stream_wrap`), `dns` for loopback, `http_parser`, Service Worker preview bridge and WebSocket bridge (ADR-0014). `node server.js` renders in a preview iframe |
| **M1d** | **Packages** ✅ | `zlib`, crypto hashes, a fast installer behind `npm install` (registry via `fetch`, integrity, bin links, native→Wasm substitution per ADR-0006), `npm run`/`npx`, `sh` as a process (ADR-0015). `npm create vite` + `npm install` succeed |
| **M1e** | **Vite** ✅ | `fs.watch`, `worker_threads`, `node:wasi` and N-API for `wasm32-wasi` addons (Rolldown), a warm Worker pool (ADR-0016). `npm run dev` serves the app with HMR |
| **M1f** | **Runtime isolation** ✅ | The kernel moves into a cross-origin-isolated iframe on its own origin, behind an async host SDK (ADR-0009, ADR-0017). Embedding pages no longer need COOP/COEP, and previews connect to the runtime frame |

## M1a approach

Node's JavaScript (`lib/`, 372 files, 5.4 MB) runs unmodified. What we write is the part Node
implements in C++:

- **The realm.** Primordials, private symbols, compiling builtins with the same parameter lists as
  `src/builtin_info.h`, and the bootstrap order of `src/node_realm.cc`:
  1. per-context scripts
  2. `internal/bootstrap/realm`, then `node`, then `web/*`, then the thread and process-state switches
  3. one `internal/main/*` script
- **The process object** that C++ creates before bootstrap.
- **Bindings.** `internalBinding()` returns TypeScript implementations backed by kernel syscalls.
  Unknown bindings and unknown properties resolve to tracing stubs. Boot proceeds, and a coverage
  report shows exactly what was touched.
- **The event loop.** libuv semantics: referenced handles and requests keep the process alive.
  Callbacks into JavaScript run inside a callback scope that drains `process.nextTick` and promise
  rejections, as `InternalCallbackScope` does.

### Binding priorities

Counts are properties used by `lib/` (from `scripts/scan-bindings.mjs`).

| Priority | Bindings |
|---|---|
| Boot | builtins, module_wrap (stub), errors, util, types, symbols, constants, config, options, process_methods, credentials, async_wrap, task_queue, timers, trace_events, mksnapshot, performance, messaging, worker, url, buffer, string_decoder, encoding_binding, os, uv, fs, modules, contextify, report, inspector, heap_utils, permission, wasm_web_api, … |
| M1a features | fs (complete), fs_dir, spawn_sync, process_wrap, pipe_wrap (stdio), tty_wrap, stream_wrap, signal_wrap, cjs_lexer |
| Later | tcp_wrap, cares_wrap, http_parser (M1c) · zlib, crypto (M1d) · fs_event_wrap, worker (M1e) |
| Not planned for M1 | quic, http2, inspector, tls_wrap, sqlite, sea, profiler |

### Distribution

`@webcore/node-lib` vendors `lib/` (plus the `acorn` and `minimatch` deps it loads) at a pinned tag
and builds one bundle (ADR-0012). The kernel loads it once into shared memory, and every Node process
decodes only the modules it actually requires.

## M1a status

| Exit criterion | Status |
|---|---|
| `/usr/bin/node` runs Node v24.21.0's own `lib/` over kernel bindings | ✅ Browser and headless |
| The M0 end-to-end suite passes unchanged | ✅ 26/26, plus 13 new real-Node tests (`test/node.test.ts`) |
| The M0 shim is deleted | ✅ |
| A curated slice of Node's `test/parallel` passes | ⏳ Next: needs `test/common` and a runner |

What works:
- **Bootstrap, runtime and modules:** the real bootstrap, CommonJS loader, `-e`/`-p`/stdin/script entry
  points, `nextTick`/microtask/immediate/timer ordering, `beforeExit`/`exit`/`exitCode`, and
  Node-formatted uncaught errors.
- **Core APIs:** `fs` (sync, callback, promises, streams), `Buffer`, `string_decoder`, `URL`, `path`,
  `os`, `util`, `events` and `stream`.
- **child_process:** `spawn` with stdio pipes, `execFile`, `spawnSync` with timeouts, and `kill`.

55 of the 72 public builtin modules load. The other 17 are tracked in `test/node.test.ts` and
scheduled for later sub-milestones:
- `http*` (M1c)
- `crypto`, `tls`, `https` and `zlib` (M1d)
- `repl` (vm contexts)
- `node:test` (V8 serializer)
- `inspector` and `trace_events`, which are absent from official builds without them too

Measured startup for one Node process: 35–60 ms in a production browser build and 100–140 ms headless.
Real Node's own startup is 20–40 ms.

### What M1a taught us

- **Node replaces the globals our bindings use.** `URL`, `TextEncoder`, `performance`,
  `queueMicrotask`, `atob` and `structuredClone` are all overwritten during bootstrap, and Node's
  versions call back into our bindings. A binding that reads the global at call time recurses
  forever. Bindings use primitives captured before bootstrap (`personalities/node/host.ts`).
- **Headless, the Worker is already a Node environment.** Real Node's lazy `Response`/`fetch` globals
  coexist with ours. Web classes for overrides are captured before bootstrap and passed through our
  own `webcore` binding.
- **Missing binding properties must read as `undefined`.** Early tracing stubs returned no-op
  functions, which masked classes needed at load time and broke `lib/`'s `binding.x ??= …` caching.
  The trace now records the access and returns `undefined`, like a real binding object.
- **Explicit vs implicit microtasks.** Node drains `process.nextTick` from C++ and runs V8's
  microtask queue explicitly; browsers run it implicitly. The loop watches writes to `tickInfo` and
  `immediateInfo` (Proxies), so ticks queued from promise reactions still drain.
- **Some work belongs in the kernel.** Running `spawnSync` inside the kernel, which can wait on
  several pipes at once, removed the stdout/stderr drain deadlock the M0 shim had.

## M1b status: done

`create-vite` 9.2.1, the real npm package and an ES module CLI, scaffolds a React app on the kernel.
It takes 126 ms in the browser (fetched straight from the npm registry by the playground) and 192 ms
headless (`test/esm.test.ts`).

ES modules are compiled to two-phase generators (ADR-0013) and driven by Node's own ESM loader
through a `module_wrap` binding. What works:
- **Module graphs:** static and dynamic imports, live bindings, `export *` and `export * as`,
  cycles with function hoisting, and top-level await.
- **`import.meta`:** `url`, `filename`, `dirname` and `resolve`.
- **Interop:** JSON modules with import attributes, `node:` builtins, and CommonJS in both directions
  (named-export detection, `require(esm)` with the `__esModule` facade, `import()` from CommonJS and
  from `-e`).
- **Resolution:** conditional `exports`, `--input-type=module`, and module-syntax detection.
- **Errors:** Node-shaped, with `file://` URLs and original line numbers.

### What M1b taught us

- **A generator gives you ESM's two phases for free.** Starting it hoists declarations and runs the
  export getters' prologue; resuming it runs the body. This avoided a declaration-hoisting
  transform, kept line numbers intact, and preserved real TDZ semantics.
- **Real-world code is the test that matters.** create-vite's minified bundle reuses short names
  (`e`, `t`, `i`) for both imports and loop variables. That exposed a duplicate `case` that disabled
  `for…of` scoping, which the hand-written test had only passed by coincidence. The test now checks
  the loop value itself, and a mutation check confirms it catches the bug.
- **Node 24 moved more JavaScript into C++.** `cjs-module-lexer` (now a C++ binding that returns a
  `Set`) and `import.meta.dirname`/`filename` (now `modules.setLazyPathHelpers`) both needed
  bindings. Vendored `lib/` alone wasn't enough.

## M1c status: done

`node server.js` renders in the playground's preview pane. The server is Node's own `http` module,
in a Worker, behind a Service Worker on `p3000.localhost`. Starting a server opens the preview,
stopping it marks the port closed, and restarting it reloads the preview.

What works:
- **Kernel sockets:** `listen`/`accept`/`connect`/`shutdown` over pipe pairs, with ephemeral ports,
  `EADDRINUSE`/`ECONNREFUSED`/`ENETUNREACH`, IPv4-mapped peer addresses on dual-stack listeners,
  and `net.listen`/`net.close` events.
- **Node:** `net` and `http` between processes and within one, with keep-alive, chunked bodies,
  trailers, `HEAD`, upgrades (the `upgrade` event), and `400` for malformed requests.
  `dns.lookup('localhost')` returns both families, so `net.connect(port)` runs happy eyeballs and
  reports an `AggregateError` exactly as Node does on macOS. Other hostnames fail with `ENOTFOUND`.
- **`http_parser`:** a TypeScript HTTP/1.1 parser with llhttp's semantics and error codes
  (`src/lib/http-parser.ts`). The bridge uses it too, to read responses.
- **Preview:** the Service Worker, boot page and client script (ADR-0014), served by the
  `@webcore/kernel/vite` plugin in dev, `vite preview` and builds. Navigations, `fetch` from the
  page, the address bar, a cookie jar per port, and WebSockets (text and binary, with
  subprotocols), verified in the browser and in `test/preview.test.ts`.

Numbers (headless): a Node server is listening 150 ms after spawn. Sequential requests from the
host take 0.2–0.3 ms each, and an 8 MiB response streams at about 800 MiB/s.

Moved out: outbound `http(s)` to M1d, because `https` needs `tls` and therefore `crypto`. Unix
domain sockets (`pipe_wrap` listen/connect), UDP and HTTP/2 are not scheduled yet.

### What M1c taught us

- **Pipes made sockets cheap.** A connection is two kernel pipes, so blocking reads, backpressure,
  half-close and EOF already worked. The new kernel code is about 250 lines.
- **Node's http server has a JavaScript path for sockets it can't consume natively.** Its C++
  parser normally reads straight from the socket's StreamBase (`parser.consume`). Making
  `consume()` a no-op sends bytes through `'data'` events instead, a path Node supports for any
  non-native socket. Nothing in `lib/` had to change.
- **Compare with real Node before believing a test.** Two first-run failures were wrong
  expectations: real Node also reports `AggregateError` with an empty message for refused
  `localhost` connections, and keeps a header name's case as `setHeader` received it.
- **A Service Worker is a narrow pipe.** It can't set cookies, can't see WebSockets, is stopped
  when idle, and can't reach a page on another origin. Each limitation needed its own piece:
  a cookie jar, a `WebSocket` replacement, a reconnect protocol, and channels handed over through
  the preview page.
- **Vite loads linked workspace packages with plain Node.** Node 22 can't import `.ts` from a Vite
  config, so the plugin is JavaScript with a `.d.ts`.

## M1d status: done

In the browser, `npm create vite@latest my-app -- --template react` scaffolds the app in 0.8 s, and
`npm install` installs its 28 packages from registry.npmjs.org in 2.4 s. The resolved tree matches
real npm's version for version. The only differences are the platform packages: native binaries
for other platforms are left out, and Rolldown's wasm32-wasi build is added.

What works:
- **npm and npx** (ADR-0015): our own installer and script runner, written in TypeScript and run as
  processes on webcore's Node.
  - **Install:** `install`/`ci`/`uninstall`, a hoisted layout like arborist's, `package-lock.json`
    v3 (reused when still valid), and `.bin` symlinks. Native packages are swapped for their
    wasm32-wasi builds (ADR-0006).
  - **Scripts:** `run` with pre and post scripts and npm's environment.
  - **Executables:** `exec`/`npx` with a cache, and `init`/`create`.
- **sh:** a POSIX-subset shell that runs commands on kernel pipes and `spawn`. Node's
  `child_process` uses it for `shell: true`, `exec` and `execSync`.
- **Kernel:**
  - symbolic and hard links (`lstat`, `readlink`, `symlink`, `link`, `realpath`; exec through a
    link keeps Linux's `argv[1]`)
  - process groups, with `kill(-pgid)`; Ctrl+C reaches a whole job
  - `extract`, which unpacks a package tarball in one syscall
- **zlib:** deflate, inflate, gzip, unzip, raw, dictionaries, streams, and `crc32`, over pako (a
  port of zlib). The output matches Node's byte for byte.
- **crypto:**
  - MD5, SHA-1 and SHA-2 digests, HMAC, PBKDF2, HKDF, random, `timingSafeEqual`, secret
    `KeyObject`s
  - WebCrypto `digest`, HMAC `sign`/`verify`/`generateKey`, PBKDF2 and HKDF `deriveBits`, and
    `getRandomValues`
  - Results match OpenSSL. Ciphers, signatures, asymmetric keys and TLS throw Node's own error
    codes (`ERR_CRYPTO_UNKNOWN_CIPHER`, `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM`).
  - 66 of 72 builtin modules load.
- **Event loop:** pending host `fetch` calls and body reads now keep a Node process alive, as
  undici's sockets do in real Node.

Numbers (browser): `npm install` 2.4 s for 28 packages (7.3 MB of tarballs, network-bound); `sh -c`
of a small script 0.1 s; a crypto one-liner 75 ms.

Not done, and why:
- **Outbound `http(s)` through Node's `http`/`https` modules.** It needs either a TLS
  implementation or a fetch-backed TLS shim inside `tls_wrap`. Global `fetch` already reaches the
  network, and the M1 exit criterion doesn't need either module, so this moves after M1e.
- **Dependencies' install scripts** are skipped and listed (ADR-0015).
- **Brotli and zstd** throw. No Wasm or JavaScript build is bundled yet.
- `npm run dev` gets as far as Vite loading Rolldown's wasm32-wasi binding, which needs
  `node:wasi`, N-API and `worker_threads`: M1e.

### What M1d taught us

- **The shortest path to compatibility was npm's results, not npm.** The lockfile and the
  `node_modules` layout are the interface other tools depend on. Reproducing arborist's placement
  rule gave the same tree as npm on the first real-world run.
- **Some work belongs in the kernel again.** Unpacking costs three syscalls per file from a
  process. One `extract` call per package lets the kernel use native gunzip and WebCrypto.
  Starting downloads during resolution then halved install time.
- **webcore's own programs can use the ABI directly.** `sh` runs commands with `pipe` and `spawn`
  on explicit fds, as a C shell does, instead of Node's stream wrappers. That made pipelines,
  redirections and builtins inside pipelines straightforward.
- **Hidden liveness bugs.** A Node process exits when its loop has nothing left. Host promises such
  as `fetch` and raw async syscalls were invisible to the loop, so a script awaiting them could
  exit early. They are now counted as pending requests, as libuv counts its requests.
- **Node 24 moved crypto state into native slots.** KeyObject and CryptoKey data now live in C++
  slots, and WebCrypto jobs return Promises. A survey of the binding contract (load-time surface,
  error shapes, slot layouts) before writing code meant every value matched OpenSSL on the first
  run.
- **Reuse the reference implementation when its API fits.** pako keeps zlib's `z_stream` API,
  which maps field for field onto Node's binding. Its output and its error messages
  ("incorrect header check") are zlib's.

## M1e status: done

In the browser, `npm run dev` in the create-vite React app starts Vite 8.3.4 in 0.7 s. The app
renders in the preview pane, and editing `src/App.jsx` updates it in place (HMR). From an empty
kernel, through the playground's buttons:

| Step | Browser | Headless |
|---|---|---|
| `npm create vite@latest my-app -- --template react` | 0.7 s | 1.4 s |
| `npm install` (28 packages) | 2.6 s | 2.6 s |
| `npm run dev`, until Vite is ready | 0.7 s | 1.1 s |

What works:
- **Threads** (ADR-0016): `threadSpawn`, `threadWait` and `threadTerminate`. A thread is a Worker
  inside its process, sharing the pid, file descriptors and working directory.
- **`worker_threads`:**
  - `Worker` from files, ES modules or `eval`, with `workerData`, `env`, `argv` and `execArgv`
  - `parentPort`, `MessageChannel` and `MessagePort`, with transfer lists (ArrayBuffers and ports)
    and `receiveMessageOnPort`
  - `BroadcastChannel`, and `SharedArrayBuffer` with `Atomics` between threads
  - `terminate()` (busy loops too), exit codes, and errors that arrive with their class, message,
    stack and properties
- **`node:wasi`**, sharing one preview1 implementation with the kernel's WASI personality.
- **N-API for wasm32-wasi addons:** napi-rs packages bring emnapi, an N-API in JavaScript, so they
  need only `node:wasi` and `worker_threads`. Rolldown's binding loads and runs its pool of four
  threads.
- **File watching:** a `watch` syscall returns an fd that reads like inotify, fed by the kernel's
  `fs.change` events. On top of it: `fs.watch` (also recursive), `fs.promises.watch`, and
  `fs.watchFile` (which polls).
- **V8's serializer:** the `serdes` binding implements V8's ValueSerializer format. For common
  values `v8.serialize` writes the same bytes as Node. `node:test` runs, including `node --test`.
- **Warm Worker pool:** the browser host keeps two Workers booted
  (`webProcessHost({ warmWorkers })`), so a spawn doesn't wait for a Worker script to load.
- **Node's realm hides globals Node doesn't have** (`window`, `document`, `self`, `location`, …).
  Libraries that check for a browser take their Node paths.
- **`http2`** loads (constants and settings). Sessions throw `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM`.
  68 of 72 builtin modules load. The rest are `repl` (vm contexts) and the inspector and trace
  modules, which official builds without them lack too.
- **Event loop:** pending `WebAssembly.compile`/`instantiate` calls and queued close callbacks keep a
  process alive.

Not done, and why:
- **The runtime iframe** (ADR-0009) is now M1f. It changes how a page embeds webcore (an async SDK,
  a runtime origin, previews that connect to the runtime frame), and nothing in Vite depends on it.
- **No synchronous receive across threads:** `Atomics.wait` followed by `receiveMessageOnPort()`
  only works within a thread (ADR-0016).
- **Hidden tabs are slow.** Browsers throttle background pages: `npm create` took 18.5 s in a
  background tab and 2 s in a visible one. The numbers above are from a visible tab.
- **Outbound `http(s)`** through Node's modules still needs TLS (see M1d).

### What M1e taught us

- **Faster exit checks found hidden liveness bugs.** The exit check moved from two nested
  `setTimeout(0)` calls, which browsers clamp and throttle, to a MessageChannel task. A process then
  exited before its child's output arrived (a close callback was queued but not counted), and
  while `WebAssembly.compile` was still running. libuv counts closing handles, and Node keeps the
  loop alive for V8's background compiles. Both now count as pending work here too.
- **Measure in the conditions users have.** One cold start of Vite took 20 s, but it didn't
  reproduce in a visible tab. Chrome also caches compiled wasm per renderer process, so the cold
  case needs a module it hasn't seen. Adding a random custom section to Rolldown's 11 MB module
  gave a cold compile and load: 0.3 s.
- **A shared global object leaks the browser.** Node's realm runs on the Worker's global object.
  `self` there is a getter-only property, so Rolldown's thread script, which sets `self` with
  `Object.assign(globalThis, …)`, threw. Real Node has no `self`, so the realm now hides every
  global Node doesn't have.
- **Host channels don't order each other.** A thread's end, its env port and its `parentPort` are
  three channels. Under load, the parent heard of the exit before `parentPort` messages arrived,
  and Node's exit handler dropped them. The thread's exit notice now lists how many messages it
  sent on each channel, and the parent waits for them (ADR-0016). A stress test (16 threads, 200
  messages each) lost messages without the wait and none with it.
- **Byte compatibility is the test.** The serializer was checked against the host Node's
  `v8.serialize` on a corpus of values, and its test compares bytes. Integer and string
  representations, padding before two-byte strings, holes and object references all matched.

## M1f status: done

The playground no longer runs the kernel. It loads `@webcore/sdk` (15 KB), which starts the runtime
in an invisible iframe on `webcore.localhost:5190`. The playground page itself isn't cross-origin
isolated. The whole flow works through the SDK: `npm create vite`, `npm install`, `npm run dev`,
the preview, and HMR from an edit made with `runtime.fs.writeFile`. Both the dev servers and the
production builds were verified.

What works:
- **Self-isolating runtime frame** (ADR-0017): `Document-Isolation-Policy` gives the frame and its
  Workers cross-origin isolation under a page that has none. It was checked first with a minimal
  experiment, then with the real runtime. An embedder that is isolated itself works too, which is
  the setup for browsers without DIP (`WEBCORE_ISOLATE=1 pnpm --filter @webcore/playground dev`).
- **`@webcore/sdk`:** `connect({ url })` returns a `Runtime`:
  - `fs`: `readFile`, `writeFile`, `mkdir`, `readdir`, `stat`, `rm`, `rename`, with `fs.change`
    events like a process's
  - `spawn` (stdin, stdout, stderr, `kill`, an abort signal for Ctrl+C) and `exec`
  - `createShell()` sessions that keep `cd` and `export` between lines
  - `events.subscribe()` for kernel events
  - `previewUrl()`, `previewPortOf()`, and relaying preview channels to the runtime
  - `close()`
- **`@webcore/runtime`:** the runtime as a static site, with the isolation headers and the preview
  assets. `serveRuntime()` is its half of the protocol. It doesn't depend on the DOM, so
  `test/runtime.test.ts` drives the SDK and the runtime over a Node MessageChannel.
- **Preview channels are bound to their port.** A preview can fetch only from the server it
  previews. WebSockets may still connect anywhere, as in a browser.
- **Kernel host API:** `mkdir`, `remove` and `rename` from outside any process, emitting events
  like `writeFile` does.

Numbers (Chromium, with the Browser pane hidden, so background priority applied):
- The first run on a cold runtime server took 2.2 s for `npm create`, 4.7 s for `npm install` and
  2.5 s until Vite was ready.
- Repeated `npm run dev` runs took 0.8 to 6 s until ready. Worker timers aren't throttled in
  hidden pages (1000 `setImmediate`s took 9 ms), so the spread comes from the lower process
  priority of hidden pages.
- The production playground was ready 0.1 s after navigation, with its assets cached.

Not done, and why:
- **Firefox and Safari** weren't tested. Until they ship DIP, they need an isolated embedder
  (ADR-0017).
- **No hosted runtime.** `connect()` takes the runtime's URL. A hosted default and deployment
  recipes (wildcard preview domains, headers) come with the first public release.
- **Restricting embedders** is left to deployments (CSP `frame-ancestors`).

### What M1f taught us

- **Check the platform before designing on it.** ADR-0009 assumed a frame could be isolated without
  its embedder. A 40-line experiment confirmed it with Document-Isolation-Policy, including Workers
  and `Atomics.wait`, before any SDK code existed.
- **Keep protocol code off the DOM.** The SDK client and the runtime server only need a
  MessagePort. The whole protocol is tested headless, and the browser only adds the window
  handshake.
- **Relaying exposed an old gap.** Since M1c, a preview's channel could fetch from any port,
  including other previews' servers with their cookies. Knowing the sender's origin at relay time
  made binding a channel to its port a few lines.
- **Async everywhere changes small things.** The playground's "Edit App.jsx" action read and wrote
  the VFS synchronously. Through the SDK it is two awaited calls, and the example buttons await
  actions.
